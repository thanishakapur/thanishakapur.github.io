Fenwick & West LLP/Jul 2026 - Present

Complaint Intake Automation

The question I was forced to answer: how does a newly filed complaint actually reach the attorney who needs it

The problem

Getting a new complaint to the right attorney meant manually cross-referencing two separate systems every time, pulling the litigation support team away from higher-value work.

What I did

  • Built an automation that triggers the moment a docket alert email arrives in a shared inbox
  • Extracts the case identifiers and queries the firm's case-document repository
  • Cross-references the result against a separate legal analytics platform to fill in case context
  • Returns the complaint file straight to the requesting attorney, with safeguards against duplicate processing

What made it hard

  • The two systems used incompatible case-number formats
  • API behavior did not match its own documentation
  • Built a classifier to flag edge cases, like patent filings needing special handling
  • Worked with IT around an authentication limitation before the workflow could run unattended
StackWriter Playbooks, REST APIs, Lucene query syntax, Microsoft Outlook and 365, Azure and Graph API
My partArchitected the workflow end to end, reverse engineered two undocumented APIs, built the edge-case classifier, led the handoff
StatusLive, handed off, and now maintained by the litigation support team

Fenwick & West LLP/Jul 2026 - Present

AI Efficiency Analysis

The question I was forced to answer: how much time did the firm's AI tools actually save, and how do you know

The problem

The firm wanted to show Amazon how much time AI tools had actually saved across its patent litigation matters, but a simple before-and-after average would have overstated the case.

What I did

  • Designed a measurement methodology comparing AI-assisted work against historical, complexity-matched matters instead of a flat average
  • Parsed and classified thousands of raw time-entry records to determine which entries actually involved AI work
  • Built the Excel workbook and audit trail behind every number, with a confidence rating on each calculation

What made it hard

  • Found two versions of a savings figure using different baselines
  • Found a baseline that had been chosen in a way that circularly matched the result it was meant to test
  • Caught both before Amazon saw them
StackPython, pandas, openpyxl, Excel with SUMIFS
Scope60-day review, four litigation workflows, thousands of billing records
My partDesigned the methodology, built the analysis infrastructure, caught the errors, briefed senior stakeholders
StatusDelivered as the basis for a deliverable presented to Amazon

Fieldhouse Staffing Prioritization Tool

The question I was forced to answer: which fieldhouses are understaffed relative to the rest of the system

The problem

Staffed-hour planning across 232 fieldhouses was decided one site at a time, with no common scale to compare a site against the rest of the system.

What I did

  • Built an Excel decision-support tool consolidating seven operational metrics into one comparable score per site
  • Ran stakeholder interviews to surface implementation constraints a purely quantitative model would have missed
  • Delivered the scoring tool plus recommendations the district could act on

What made it hard

  • A composite score only works if it does not hide the tradeoff underneath it
  • Kept every component metric visible next to the total, since a low score on one dimension and a low score across all seven call for different responses
StackExcel scoring model, qualitative synthesis from stakeholder interviews
Scale232 fieldhouses, 7 operational metrics
My partConsultant on a student team, working on metric structure, the tool build, and client recommendations
StatusDelivered, and rerunnable as the underlying data updates

The question I was forced to answer: which survey responses are clean enough to analyze

The problem

Raw Prolific and JATOS exports are not analysis-ready, and someone has to decide which responses count every time new data comes in.

How I work

The pattern repeats across these projects.

  • An organization makes the same decision over and over, informally
  • It is expensive because it is manual, and inconsistent because everyone does it slightly differently
  • My job is to get the rule written down in a form that holds up against real data, then build the thing that runs it
  • Getting a pipeline to run is easier than getting people to use it, and only the second one changes how an organization works
  • Long term I want to work in technology IP and patent law, and right now I am building a working understanding of how these systems actually get put together
